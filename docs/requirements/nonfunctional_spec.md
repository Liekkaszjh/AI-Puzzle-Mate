# 软件系统非功能规格说明书

## 1. 引言与范围

### 1.1 文档目的

规定本项目在性能、可靠性、安全、AI 输出质量、易用性、可维护性、可观测性和兼容性方面的质量要求，为后续设计、开发、测试、发布及课程验收提供可核对的依据。

### 1.2 适用范围

适用于 V1.0 单人游戏 MVP：创建游戏、AI 题目生成与审核、汤主问答、AI 队友推理、提示、答案判定和游戏复盘。排行榜、多人在线、付费等扩展能力暂不纳入本版验收。

### 1.3 编号和优先级

NFR-x.y 表示非功能需求；P0 为发布阻断项，P1 为 V1.0 应完成项，P2 为可按资源安排的改进项。每条需求包括目标指标与验证方法。

### 1.4 重要声明

本文指标为课程项目的建议验收目标，尚未通过性能基准测试验证。团队应在系统设计阶段评审数值，并记录批准后的变更，不应将建议目标误写为当前已达到的事实。

## 2. 术语、假设与测试边界

### 2.1 术语表

| 术语 | 解释 |
|---|---|
| P95 | 第 95 百分位响应时间；95% 请求的耗时不高于该数值。 |
| MVP | 最小可行产品，指实现完整可玩的核心流程。 |
| LLM | 大语言模型；由外部模型服务提供推理能力。 |
| 越权访问 | 未经授权读取、操作其他角色或其他会话的数据。 |
| 测试集 | 预先准备且含期望结果的可复现测试样例集合。 |

### 2.2 测试环境与约定

- 测试基线环境：后端建议使用 2 vCPU、4 GB 内存的固定实例，数据库独立或明确部署方式；前端在常见桌面浏览器运行。实际配置需在测试报告中记录。
- 性能测试需记录模型提供方、模型版本、网络条件、并发数、样本数和测量时间；非 AI 接口延迟与 LLM 端到端延迟分开统计。
- 第三方模型服务的限流与故障不可完全由本系统控制；本系统仍须提供超时、重试引导和清晰的故障信息。
- 如 V1.0 未实现账号系统，则“用户”与“会话”权限按临时会话标识及服务端控制实现，不虚构登录和账户功能。

## 3. 非功能需求清单

### 3.1 性能与响应时间（Performance）

| 编号 | 优先级 | 需求描述 / 验收指标 | 验证方法 |
|---|---|---|---|
| NFR-1.1 | P0 | 非 AI 常规接口（创建会话、查询会话、获取历史记录）的第 95 百分位响应时间（P95）不超过 1 秒。 | 在约定测试环境中，以 20 个并发虚拟用户执行至少 200 次请求；分别统计 API 延迟与失败率。 |
| NFR-1.2 | P0 | 正常网络及模型服务可用时，AI 汤主单轮问答端到端 P95 响应时间不超过 20 秒；超过 35 秒应提示超时并支持重试。 | 使用 100 条标准问句测试，记录输入提交至结果显示的时间；超时场景单独注入验证。 |
| NFR-1.3 | P1 | 单次题目生成端到端 P95 不超过 45 秒；审核失败最多自动重新生成 3 次，最终失败须向用户说明。 | 以 50 次生成任务测量首次生成响应；另模拟审核失败及上游错误，检查重试上限与提示。 |
| NFR-1.4 | P1 | 系统至少支持 20 个并发游戏会话进行创建、提问、查看记录等操作，不能发生会话串扰。 | 执行 20 并发用户的混合业务测试，检查成功率及不同 sessionId 的数据隔离。 |

### 3.2 可靠性与故障恢复（Reliability）

| 编号 | 优先级 | 需求描述 / 验收指标 | 验证方法 |
|---|---|---|---|
| NFR-2.1 | P0 | 在受控测试环境、模型服务可用的前提下，核心业务接口（创建游戏、保存问答、提交答案）请求成功率应达到 99% 以上。 | 执行至少 300 次自动化接口请求；将第三方 LLM 故障单独统计，不混入本系统接口缺陷指标。 |
| NFR-2.2 | P0 | 遇到模型调用超时、网络断开或接口异常时，系统须给出可理解的错误信息，不得将失败回复误记为有效问答。 | 模拟网络中断、返回异常及超时，检查错误提示、数据状态和重新发起操作能力。 |
| NFR-2.3 | P1 | 在同一浏览器有效会话内刷新或重新进入页面后，应能够恢复已保存的当前游戏及问答记录。 | 准备 30 个含问答记录的会话并刷新、重新进入；验证数据及游戏状态恢复正确。 |
| NFR-2.4 | P0 | 游戏开始后，关联的原始汤底与关键事实不可被问答流程意外修改；状态转换不得出现“已结束又继续提问”等非法操作。 | 通过服务端单元测试和接口测试验证题目快照不变、状态机合法性。 |

### 3.3 安全性与数据保护（Security & Privacy）

| 编号 | 优先级 | 需求描述 / 验收指标 | 验证方法 |
|---|---|---|---|
| NFR-3.1 | P0 | 大模型 API Key 等密钥只允许保存在服务端环境变量或密钥管理配置中，不得出现在前端代码、浏览器请求或公开仓库。 | 检查前端构建产物、网络请求、仓库扫描结果和服务端配置。 |
| NFR-3.2 | P0 | AI 队友仅能接收汤面、公开问答、已确认线索与已解锁提示；任何接口不得向 AI 队友返回完整汤底或未解锁提示。 | 设计至少 30 个越权与提示词注入测试用例，检查传入队友的上下文及接口返回字段，泄露数须为 0。 |
| NFR-3.3 | P0 | 玩家与管理员的受保护操作必须经过服务端权限校验；不同游戏会话数据不得发生越权读取或篡改。 | 进行会话 ID 替换、未登录/低权限访问和管理接口测试；预设越权用例通过率 100%。 |
| NFR-3.4 | P1 | 日志中不得记录 API Key、完整汤底等敏感信息；用户输入与会话记录仅在业务必要范围内保存，并提供配置化清理机制。 | 检查日志脱敏样例、数据库留存策略及按配置删除历史记录的结果。 |
| NFR-3.5 | P1 | 系统须限制超长输入和异常频繁请求：单条提问长度上限建议 1000 字，每会话每分钟不超过 10 次 AI 请求。 | 使用边界值与频率测试，验证错误码、提示文案和服务端限流生效。 |

### 3.4 AI 输出质量与内容安全（AI Quality & Safety）

| 编号 | 优先级 | 需求描述 / 验收指标 | 验证方法 |
|---|---|---|---|
| NFR-4.1 | P0 | 新生成题目须经过安全审核；在预先准备的 100 条高风险测试样例中，严重不适宜题目不得通过审核。 | 运行固定安全测试集并人工复核；严重违规样例漏检数为 0。该指标不代表对所有生成内容的绝对保证。 |
| NFR-4.2 | P0 | 在人工标注的至少 100 条可判断问题测试集中，AI 汤主“是 / 不是 / 无关”分类准确率目标不低于 95%。 | 固定汤底、输入与标准标签后运行评测，按准确数 / 可判定总数统计；模糊问句独立测试。 |
| NFR-4.3 | P0 | 针对同一汤底中语义相同或等价的提问，AI 汤主回答应保持一致；不得在正常问答中直接暴露完整汤底。 | 准备至少 50 组同义改写问题和 30 条剧透诱导测试，检查冲突数及未授权泄露。 |
| NFR-4.4 | P1 | 答案判定在人工标注的至少 60 份玩家答案中，与预期“正确 / 部分正确 / 错误”一致的比例不低于 90%。 | 使用覆盖三种类别及边界答案的测试集，计算总体一致率并记录误判案例。 |
| NFR-4.5 | P1 | AI 队友的主动互动应可控，不得未经请求持续刷屏；主动发言需要遵循可配置的间隔或触发规则。 | 在至少 20 局模拟会话中检查主动消息频率、玩家可关闭功能及提示访问边界。 |

### 3.5 易用性与可访问性（Usability & Accessibility）

| 编号 | 优先级 | 需求描述 / 验收指标 | 验证方法 |
|---|---|---|---|
| NFR-5.1 | P1 | 首次进入游戏的用户应在不查看说明的情况下，完成主题/难度选择并进入问答界面；核心任务完成率目标不低于 80%。 | 招募至少 10 名未参与开发的试用者，按统一任务脚本记录是否独立完成。 |
| NFR-5.2 | P1 | 主要页面须适配宽度 360px 至 1440px 的常见屏幕，核心按钮与问答内容不得横向溢出或被遮挡。 | 分别在移动端和桌面端视口进行页面回归测试与人工检查。 |
| NFR-5.3 | P1 | AI 正在生成、调用失败、已提交、游戏结束等关键状态应提供清晰反馈；关键交互须支持键盘操作。 | 采用可用性检查清单，验证加载提示、错误提示、按钮焦点及键盘提交/切换。 |

### 3.6 可维护性与可扩展性（Maintainability & Extensibility）

| 编号 | 优先级 | 需求描述 / 验收指标 | 验证方法 |
|---|---|---|---|
| NFR-6.1 | P1 | 系统应将游戏业务逻辑、AI Agent、模型适配层和数据访问层分离；更换模型提供方不应要求重写游戏主流程。 | 设计审查模块依赖图，并以模拟模型适配器替换完成一轮核心流程测试。 |
| NFR-6.2 | P1 | 核心非 AI 业务逻辑（会话状态机、输入校验、答案记录等）的自动化单元测试行覆盖率目标不低于 70%。 | 执行覆盖率工具并提供报告；不将外部 LLM 真实调用纳入单元测试覆盖率分母。 |
| NFR-6.3 | P1 | 代码合入主分支前应通过基本静态检查、自动化测试和至少 1 名非提交者的 Pull Request 审查。 | 检查 GitHub Actions / PR 记录及分支保护配置。 |
| NFR-6.4 | P2 | 主要 API、数据模型和 Agent 输入输出须保留版本化说明文档，功能变更时同步更新相关需求编号。 | 抽查变更 PR，确认接口文档、Schema 和 FR 追踪记录已更新。 |

### 3.7 可观测性（Observability）

| 编号 | 优先级 | 需求描述 / 验收指标 | 验证方法 |
|---|---|---|---|
| NFR-7.1 | P1 | 对 AI Agent 调用记录会话标识、Agent 类型、调用时间、耗时、成功/失败状态和错误类别；日志应避免写入汤底和密钥。 | 分别触发成功、超时与失败事件，检查日志字段完整性及脱敏效果。 |
| NFR-7.2 | P2 | 系统应能统计每日模型请求次数、失败率和平均耗时，支持排查响应慢或异常问题。 | 连续运行测试数据并生成统计结果，核对统计值与原始事件一致性。 |

### 3.8 兼容性与部署（Compatibility & Deployment）

| 编号 | 优先级 | 需求描述 / 验收指标 | 验证方法 |
|---|---|---|---|
| NFR-8.1 | P1 | V1.0 应在最近两个主要版本的 Chrome 和 Edge 浏览器中完成核心流程；手机浏览器至少验证一种主流环境。 | 使用浏览器兼容性测试矩阵执行创建游戏到复盘的端到端脚本。 |
| NFR-8.2 | P1 | 开发、测试、生产环境的模型地址、密钥、数据库连接应采用独立配置，不得硬编码在业务源文件中。 | 检查部署配置和环境切换过程，确认同一代码版本可用不同环境配置启动。 |

## 5. 验收原则与交付物

- 全部 P0 非功能需求通过验收；若存在未通过项，应在发布前完成修复或由项目负责人记录明确的风险处置决定。
- 每项 NFR 对应测试用例（如 TC-NFR-3.2）及执行记录，包含测试环境、样本量、实际结果、判定、缺陷链接与复测结果。
- P1 未完成项需登记原因和计划；P2 可纳入后续 Backlog，不阻断核心 MVP，但不得以“已实现”表述。
- 以 W11–W13 为集中测试窗口，W14–W17 对生产部署和 Beta 反馈进行复测。

建议交付：非功能需求表、测试用例及数据集、性能测试报告、安全测试报告、AI 专项测试报告、缺陷与复测记录。
